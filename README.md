## 1. รู้จักทีมของคุณ

| โมเดล | Model ID | บทบาท | ถนัด |
|---|---|---|---|
| **Opus 5** | `claude-opus-5` | 🧠 สมอง | คิด ตัดสินใจ ออกแบบ แก้ปัญหายาก |
| **Sonnet 5** | `claude-sonnet-5` | ✋ มือ | ลงมือเขียนโค้ด — ค่า default ที่คุ้มสุด |
| **Haiku 4.5** | `claude-haiku-4-5` | 💪 แรงงาน | งานถึกซ้ำๆ ที่ไม่ต้องคิด ทำขนานได้เยอะ |
| **Fable 5** | `claude-fable-5` | 💬 ปาก | ภาษาสำหรับคนอ่าน — copy, microcopy, เล่าเรื่อง |

สามตัวแรกอยู่บนแกนเดียวกัน: *ฉลาด ↔ เร็ว ↔ ถูก*
Fable อยู่คนละแกน: งานของมันคือ **คำ** ไม่ใช่ **โค้ด** (และเป็นตัวที่ *แพงสุด* — ไม่ใช่ตัวรองประหยัด)

**ลำดับที่ถูกต้องเสมอ:**

```
Opus คิด  →  Sonnet ลงมือ  →  Haiku เก็บงานถึก  →  Fable เกลาคำตอนท้าย
```

อย่าให้ Fable นำหน้า — มันเขียนเพราะ แต่ไม่ได้ถูกวางมาให้คุมโครงโค้ด
โครงต้องมาจาก Opus ก่อน แล้ว Fable ค่อยแต่งหน้าให้สวย

### ราคา (USD / 1M tokens)

| โมเดล | Input | Output | Context |
|---|---:|---:|---:|
| Fable 5 | $10 | $50 | 1M |
| Opus 5 | $5 | $25 | 1M |
| Sonnet 5 | $3 | $15 | 1M |
| Haiku 4.5 | $1 | $5 | 200K |

**อ่านตารางนี้ยังไง:**
- Opus แพงกว่า Sonnet แค่ **~1.7 เท่า** ไม่ใช่สิบเท่า — ลังเลว่าจะขึ้น Opus ไหม ส่วนใหญ่คำตอบคือขึ้นเถอะ
- Haiku ถูกกว่า Sonnet **3 เท่า** — คุ้มเมื่องานเยอะพอและไม่ต้องคิด งานเดียวไม่คุ้มค่าสลับ
- **Output แพงกว่า input 5 เท่าเสมอ** ต้นทุนจริงมาจากความยาวของสิ่งที่มันเขียน ไม่ใช่ความยาวของสิ่งที่คุณส่งไป
- Fable แพงกว่า Opus 2 เท่า — ใช้เฉพาะกับ *คำ* เท่านั้น อย่าเอาไปเขียนโค้ดเพราะ "แพงกว่าน่าจะดีกว่า"

> ราคานี้คือ Claude API โดยตรง ถ้าใช้ผ่าน subscription (Pro/Max) คิดเป็นโควตาการใช้งาน ไม่ได้จ่ายรายโทเคน — แต่ตรรกะ "อะไรแพงกว่าอะไร" เหมือนกัน

## 2. สลับโมเดลยังไง

คู่มือทั้งเล่มไร้ค่าถ้าสลับโมเดลไม่เป็น มี 3 ระดับ:

**ระดับเซสชัน — เปลี่ยนตัวหลักที่คุยด้วย**

```bash
claude --model claude-opus-5
```

หรือพิมพ์ `/model` ในเทอร์มินัลเพื่อเลือกจากเมนู (ในแอป Desktop/Web ใช้ตัวเลือกโมเดลบน UI)

**ระดับ subagent — ให้ตัวถูกทำงานถึกขนานกัน**

สร้างไฟล์ `.claude/agents/test-writer.md`:

```markdown
---
name: test-writer
description: เขียน unit test ตาม spec ที่ให้ ใช้กับไฟล์ที่ logic ตรงไปตรงมา
model: haiku
tools: Read, Write, Edit, Bash, Grep, Glob
---

เขียนเทสต์ตามแพทเทิร์นที่มีอยู่ในโปรเจกต์ ห้ามแก้โค้ด production
```

แล้วสั่ง `"ใช้ test-writer เขียนเทสต์ให้ 8 ไฟล์นี้"` — ตัวหลัก (Opus/Sonnet) คุมงาน ส่วน Haiku ยิงขนาน
ค่า `model:` รับ `opus` / `sonnet` / `haiku` / `fable` / `inherit` หรือ model ID เต็มก็ได้

**ระดับ API — เขียนโปรแกรมเรียกเอง**

```python
client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    messages=[{"role": "user", "content": "..."}],
)
```

**ขนานกี่ตัวถึงคุ้ม:** งานย่อยต้อง *อิสระต่อกันจริง* (ไฟล์ไม่ทับกัน ไม่ต้องรอผลกัน) และมีตั้งแต่ ~3 ชิ้นขึ้นไป
ต่ำกว่านั้นค่า overhead ของการอธิบายบริบทให้ subagent ใหม่แพงกว่าทำเอง

## 3. คันโยกที่สำคัญกว่าการเปลี่ยนโมเดล

คนส่วนใหญ่มีปัญหาคุณภาพเพราะสองเรื่องนี้ ไม่ใช่เพราะเลือกโมเดลผิด

### 3.1 Context เต็ม — ศัตรูอันดับหนึ่ง

โมเดลเทพที่ context เหลือ 5% แพ้โมเดลกลางๆ ที่ context โล่ง

- Opus 5 / Sonnet 5 / Fable 5 = **1M tokens** · Haiku 4.5 = **200K**
- เต็มแล้วระบบจะย่อประวัติให้อัตโนมัติ (compaction) — ไม่พัง แต่ *รายละเอียดหาย* และมันจะเริ่มลืมข้อตกลงที่คุยกันไว้ตอนต้น

**กฎปฏิบัติ:**
- อย่าเริ่มงานรีแฟกเตอร์ใหญ่ตอนที่คุยมายาวแล้ว — `/clear` ก่อน แล้วเริ่มใหม่พร้อมสรุปสั้นๆ
- แตกงานใหญ่เป็นหลายเซสชัน เซสชันละเป้าหมายเดียว
- งานอ่านโค้ดเยอะๆ ให้ subagent อ่านแล้วสรุปกลับมา — บริบทของมันไม่กินโควตาเรา
- เปลี่ยนเรื่องคุย = `/clear` เสมอ ถูกกว่าและแม่นกว่าปล่อยให้ประวัติเก่าค้าง

### 3.2 Effort / Extended thinking — เพิ่มความคิดโดยไม่เปลี่ยนโมเดล

โมเดลรุ่นใหม่คิดก่อนตอบได้ และคุมความลึกได้ด้วย `effort` 5 ระดับ: `low` `medium` `high` `xhigh` `max` (ค่า default = `high`)

```python
client.messages.create(
    model="claude-sonnet-5",
    max_tokens=32000,
    thinking={"type": "adaptive"},
    output_config={"effort": "xhigh"},   # งานโค้ด/agentic ยากๆ
    messages=[...],
)
```

ใน subagent ก็ตั้งได้ผ่าน frontmatter (`effort: low` สำหรับงานถึก)

**ทำไมสำคัญ:** งานยากที่ Sonnet ตอบตื้น มัก**ไม่ใช่**เพราะต้องขึ้น Opus แต่เพราะ effort ต่ำเกิน
ลอง `xhigh` ก่อนเด้งขึ้นโมเดล — ถูกกว่าและมักพอ

**ข้อควรระวัง:** `max_tokens` นับรวมทั้งส่วนที่คิดและส่วนที่ตอบ ตั้ง effort สูงแล้วต้องเผื่อ `max_tokens` ให้เยอะ (เริ่มที่ 64K) ไม่งั้นจะโดนตัดกลางคัน

## 4. สูตรสำเร็จทุกโปรเจกต์

```
1. Opus    วางแผน + ออกแบบ            (ครั้งเดียว — จ่ายแพงตรงนี้คุ้มสุด)
2. Sonnet  ลงมือเขียน                  (ส่วนใหญ่ของงาน)
3. Haiku   subagent เก็บงานย่อยขนานกัน  (test, boilerplate, format)
4. Opus    กลับมาตอนติด + review ก่อนจบ
```

**กฎเหล็ก 4 ข้อ — ไม่มีข้อยกเว้น:**

1. **แตะเงิน = Opus** ต่อให้ดูง่ายแค่ไหน (idempotency, race, double-spend คือกับดักที่ *ดูง่าย*)
2. **auth / สิทธิ์ = อย่างน้อย Sonnet** ห้าม Haiku — validation พลาดจุดเดียว ประตูเปิดทั้งบ้าน
3. **รอยต่อระหว่างระบบ = Opus** บั๊กร้ายแรงไม่ได้อยู่ *ใน* ระบบ แต่อยู่ *ระหว่าง* ระบบ
4. **โมเดลไม่ใช่ตัวแทนของเทสต์** เงิน/สต็อก/auth ต้องมีเทสต์เสมอ ไม่ว่าใครเขียน

ข้อ 4 สำคัญที่สุดและคนข้ามบ่อยที่สุด: **Opus เขียน race condition พลาดก็ได้** ต่างกันแค่พลาดน้อยกว่า
ถ้าไม่มีเทสต์ก็ไม่มีใครรู้ว่าพลาด — และคุณจะไปรู้ตอนปิดยอดไม่ตรง
ท่าที่ถูก: **Opus เขียน logic + เขียนเทสต์เคสยาก (race, ล้มกลางทาง, ค่าติดลบ) → Haiku ขยายเคสธรรมดาให้ครบ**

## 5. แบ่งตามสายงาน

### Frontend
| งาน | โมเดล |
|---|---|
| ออกแบบ UI/UX, วาง component architecture | Opus |
| เขียน component, Figma→code, styling | Sonnet |
| แก้ CSS จิ๊บๆ, rename props | Haiku |
| debug state/render ที่งง | Opus |

### Backend
| งาน | โมเดล |
|---|---|
| ออกแบบ API, schema, data model | Opus |
| endpoint, business logic, CRUD | Sonnet |
| validation, error handling | Sonnet (ห้าม Haiku) |
| test, boilerplate, DTO | Haiku |
| debug race / N+1, optimize query | Opus |

### Mobile (iOS / Android / Flutter)
| งาน | โมเดล |
|---|---|
| ออกแบบ navigation, state architecture, offline strategy | Opus |
| เขียน screen / widget / view, ต่อ API | Sonnet |
| แก้ padding, string, asset, bump version | Haiku |
| debug build, signing, permission, crash เฉพาะเครื่อง | Opus |

มือถือมีกับดักเพิ่มจาก web: **lifecycle** (แอปถูกฆ่ากลางทาง) และ **offline** — สองอันนี้เป็นงานออกแบบ ไม่ใช่งานเขียน → Opus

### DevOps
| งาน | โมเดล |
|---|---|
| ออกแบบ CI/CD, infra architecture | Opus |
| Dockerfile, CI yaml | Sonnet |
| แก้ config, env var, bump version | Haiku |
| debug pipeline พัง (cert/network/permission) | Opus |
| Terraform / K8s | Opus ออกแบบ → Sonnet ลงมือ |

### Migration / รีแฟกเตอร์ขนานใหญ่
เคสที่ Haiku คุ้มที่สุดในบรรดาทั้งหมด — เพราะงานเยอะและซ้ำจริง

| ขั้น | งาน | โมเดล |
|---|---|---|
| 1 | วางแผน + ทำตัวอย่าง 1–2 ไฟล์ให้เป๊ะ | **Opus** |
| 2 | ยิงแพทเทิร์นเดิมใส่อีก 200 ไฟล์ | Haiku ขนาน |
| 3 | ไล่เก็บไฟล์ที่หลุดแพทเทิร์น | Sonnet |
| 4 | review ผลรวม + ไฟล์ที่แตะ logic | **Opus** |

**⚠️ migration ที่แตะข้อมูลจริง (DB schema, ลบคอลัมน์, แปลงค่า) = Opus ทั้งหมด + dry run + backup ก่อนเสมอ** ผิดแล้วย้อนไม่ได้

### อ่านโค้ดคนอื่น / debug production
| งาน | โมเดล |
|---|---|
| ไล่หาว่าโค้ดที่เกี่ยวข้องอยู่ไฟล์ไหน | subagent ตัวถูก ยิงขนาน |
| เข้าใจว่าระบบทำงานยังไง สรุปเป็นแผนที่ | Sonnet |
| debug incident ที่กำลังไหม้อยู่ | **Opus** |
| หา root cause ของบั๊กที่เกิดนานๆ ที | **Opus** |

incident ไม่ใช่เวลาประหยัด — ค่าโมเดลถูกกว่าเวลาที่ระบบล่มเสมอ

## 6. เคสจริง

### 🌐 Landing Page — งานเบา ประหยัดได้เต็มที่

```
Opus    วาง layout + สไตล์ (ครั้งเดียว)
Sonnet  เขียน HTML/CSS จริง + วนแก้กับ Preview
Fable   headline, CTA, คำโปรย
Haiku   responsive, SEO meta, เก็บรายละเอียด
```

**ท่าเร็วสุด:** Opus ทำ mockup ใน Artifact → วนแก้จนชอบ → Sonnet ขยายเป็นโปรเจกต์จริง → Fable เกลาคำ
**กุญแจ:** ส่งลิงก์เพจที่ชอบมาเป็นตัวอย่าง + บอกกลุ่มลูกค้า — ดีกว่าบอก "ทำให้สวย" ลอยๆ สิบเท่า

### 🏪 ERP / POS — งานเสี่ยงสูง แบ่งตามความเสี่ยง

| โมดูล | ความเสี่ยง | โมเดล |
|---|---|---|
| 💰 ชำระเงิน, บิล, ทอนเงิน, ปิดยอด | สูงสุด | **Opus ทั้งหมด** |
| 📦 สต็อก, ตัดสต็อก, รับเข้า | สูงสุด | **Opus** |
| 🧾 บัญชี, ledger, ภาษี | สูงสุด | **Opus** |
| 👤 พนักงาน, สิทธิ์, กะ | สูง | Opus ออกแบบ / Sonnet เขียน |
| 🛒 หน้าขาย, ตะกร้า, บาร์โค้ด | กลาง | Sonnet |
| 📊 dashboard, รายงาน, CRUD สินค้า | ต่ำ–กลาง | Sonnet |
| 🎨 ฟอร์ม, template ใบเสร็จ | ต่ำ | Haiku |

**กับดัก POS ที่ดู "ง่าย" แต่ฆ่าร้าน — ต้อง Opus:**
- ตัดสต็อก + บันทึกขาย ต้อง **atomic** (ขายแล้วสต็อกไม่ลด = ของหาย)
- สองแคชเชียร์ขายชิ้นสุดท้ายพร้อมกัน → สต็อกติดลบ
- **Offline mode** — เน็ตหลุดต้องขายต่อได้ แล้ว sync ไม่ให้ยอดชน (ยากสุดใน POS)
- ปิดยอดสิ้นวันต้องตรงเป๊ะกับบิลทุกใบ
- เงิน คำนวณเป็น integer (สตางค์) — **ห้าม float**

**ลำดับ:**
```
Phase 0  Opus   contract ขาย/สต็อก/บัญชี + แผน offline (ตัดสินใจตั้งแต่ต้น)
Phase 1  Opus   core เงิน + ตัดสต็อก        │ Sonnet  POS UI + CRUD (ขนาน)
Phase 2  Opus   เชื่อม ขาย×สต็อก×บัญชี + ปิดยอด
Phase 3  Haiku  ใบเสร็จ ฟอร์ม รายงาน test data
Review   Opus   ไล่ path เงิน+สต็อก ก่อน go-live
```

ทุก Phase ที่เป็น Opus ต้องมีเทสต์คู่มาด้วย (กฎเหล็กข้อ 4) — โดยเฉพาะเคส "ขายพร้อมกัน" และ "เน็ตหลุดกลางบิล"

### 🎨→⚙️ UI เสร็จแล้ว แต่ยังไม่ได้ออกแบบ Backend

ยังเป็นงาน "ออกแบบ" → **Opus** ไม่เปลี่ยน แต่เคสนี้มีข้อได้เปรียบ: **UI ที่เสร็จแล้ว = สเปคของ Backend ฟรีๆ**

```
ทุกหน้าจอ  → บอกว่าต้องมี API อะไร คืนข้อมูลอะไร
ทุกปุ่ม    → บอกว่าต้องมี action/endpoint อะไร
ทุกฟอร์ม   → บอกว่ารับ input อะไร validate อะไร
ทุก state  → loading/error/empty บอกว่า API fail แบบไหนได้บ้าง
```

| ขั้น | งาน | โมเดล |
|---|---|---|
| 1 | ไล่อ่าน UI ทุกหน้า → สกัดเป็น API contract | **Opus** |
| 2 | ออกแบบ data model / schema จาก contract | **Opus** |
| 3 | ตัดสินใจโครง: auth, sync/async, ownership ของ data | **Opus** |
| 4 | เขียน endpoint ตาม contract | Sonnet |
| 5 | เชื่อม UI เข้า API จริง | Sonnet |
| 6 | test, mock data, boilerplate | Haiku |

**⚠️ กับดักเคสนี้:** อย่าออกแบบ backend ตาม UI เป๊ะเกินไป — UI เปลี่ยนบ่อยกว่า backend เสมอ
- ❌ endpoint 1 อันต่อ 1 หน้าจอ (`/api/home-page-data`) → UI เปลี่ยนที backend พังที
- ✅ ออกแบบตาม **resource จริง** (`/users`, `/orders`) แล้วให้หน้าจอประกอบเอา

นี่คือเหตุผลที่ต้อง Opus — Sonnet มักออกแบบ "ตามที่ UI ขอ" ตรงๆ แต่ Opus จะถอยมามองว่า *ข้อมูลจริงของระบบคืออะไร* แล้วออกแบบให้ทนต่อการเปลี่ยน UI

### 🔗 ระบบใหญ่โยงกัน (แชต + การเงิน + สมาชิก)

หลักเดียวกับ POS: **การเงิน = Opus ทั้งหมด · สมาชิก = Opus ออกแบบ/Sonnet เขียน · แชต = Sonnet · รอยต่อ = Opus เสมอ**

ก่อนเขียนโค้ด ให้ Opus ทำ **Phase 0** ครั้งเดียว:
1. ใครเป็นเจ้าของ data อะไร (ยอดเงินอยู่ที่ระบบการเงินเท่านั้น — ห้ามเก็บสำเนา)
2. คุยกันแบบไหน (หักเงิน = เรียกตรงรอผล / แจ้งแบน = ยิง event)
3. ล้มกลางทางแล้วทำยังไง (rollback / compensating transaction)

## 7. สัญญาณว่าเลือกโมเดลผิด

ซีเนียร์เรียกมันว่า "สัญชาตญาณ" แต่จริงๆ มันคือสัญญาณที่จับได้ ถ้าเห็นข้อไหน **เด้งขึ้น Opus ทันที อย่าเสียดาย**

| สัญญาณ | แปลว่า |
|---|---|
| แก้แล้วพังที่อื่น 2 ครั้งติด | มันไม่เข้าใจว่าระบบเชื่อมกันยังไง |
| วนแก้จุดเดิมรอบที่ 3 ไม่หลุด | ติดที่การวินิจฉัย ไม่ใช่การพิมพ์ |
| เริ่มเดาแทนที่จะไปอ่านโค้ด | บริบทไม่พอ หรือความสามารถไม่พอ |
| ขอ log เพิ่มเรื่อยๆ แต่ไม่ตั้งสมมติฐาน | ไม่มีทฤษฎีว่าอะไรพัง = ยังไม่เข้าใจ |
| เสนอ workaround แทนที่จะแก้ต้นเหตุ | มันยอมแพ้กับ root cause แล้ว |
| เพิ่ม try/catch คลุมทับปัญหา | ซุกบั๊ก ไม่ได้แก้ |
| คำตอบถูกแต่ตื้น ไม่แตะเคสขอบ | ลอง `effort: xhigh` ก่อน แล้วค่อยขึ้น Opus |

**สัญญาณกลับทาง — ควรเด้ง *ลง* Haiku:**
- คุณอ่านที่มันทำแล้วคิดว่า "อันนี้ผมทำเองก็ได้ แค่ขี้เกียจพิมพ์"
- งานเดียวกันเป๊ะๆ ต้องทำซ้ำเกิน 5 รอบ
- ไม่มีการตัดสินใจอะไรเลยในงานนั้น มีแต่การพิมพ์

## 8. เรื่องที่คนเข้าใจผิดบ่อย

### "ทำ UI ให้สวย" — ความสวยไม่ได้อยู่ที่โมเดล

```
เขียน UI → เปิดดูจริง → จับจุดไม่สวย → แก้ → ดูใหม่   (วนจนสวย)
```

โมเดลกลางๆ ที่ *เห็นผลลัพธ์* แล้ววนแก้ 3 รอบ **ชนะ** โมเดลเทพที่เขียนรอบเดียวโดยไม่เคยเห็นหน้าจอ

เครื่องมือสำคัญกว่าอัปเกรดโมเดล:
- **Figma MCP** — มีดีไซน์แล้ว ดึงมาเป็นโค้ดตรงๆ ไม่ต้องเดา
- **Artifact / Preview** — เห็นของจริง วัดสี วัดระยะ แก้จากที่เห็น
- **ตัวอย่างอ้างอิง** — ลิงก์เว็บที่ชอบ 1 อัน มีค่ากว่าคำสั่ง "สวยๆ" ร้อยคำ

### วางโครงระบบ — จุดที่คุ้มค่าจ่ายแพงสุด

โครงผิด แก้ทีหลังแพงกว่าโค้ดผิด 100 เท่า → **Opus เท่านั้น** และอย่าให้คิดรอบเดียวจบ:

```
เสนอ 2–3 แนวทาง → เทียบ trade-off กับข้อจำกัดจริง → เลือก + เขียนเหตุผลว่าทำไมไม่เลือกอันอื่น
```

⚠️ กำกับด้วย: *"ให้พอดีสเกลตอนนี้ ไม่ over-engineer"* — โมเดลฉลาดชอบออกแบบเผื่ออนาคตเกินจริง

### Fable ใช้ตรงไหน

| ✅ ใช่ | ❌ ไม่ใช่ |
|---|---|
| ข้อความที่ *คนอ่าน* | โค้ดที่ *เครื่องรัน* |
| ปุ่ม, error message, empty state, onboarding | API docs ที่ต้องเป๊ะ → Sonnet/Opus |
| headline, CTA, email, push notification | logic, โครงสร้าง → Opus |
| README เล่าเรื่อง, blog, changelog | comment ในโค้ด → ตัวที่เขียนโค้ด |

**สูตร copy การตลาด:** บอก 5 อย่าง — ขายอะไร / ให้ใคร / แก้ปัญหาอะไร / โทนไหน / CTA อะไร
โครง `Hook → Value → Proof → CTA` · พูดถึง *ลูกค้า* ไม่ใช่ตัวเอง · ขอ 3–5 เวอร์ชันแล้วเลือก

**เขียนคอปปี้ภาษาไทย:** ต้องกำกับมากกว่าภาษาอังกฤษ เพราะ "โทน" ของไทยละเอียดกว่า

- บอกระดับความสุภาพให้ชัด: *ครับ/ค่ะ* หรือไม่ใส่, เรียกลูกค้าว่า *คุณ / พี่ / เพื่อน*
- บอกว่าให้ทับศัพท์หรือแปล — "ดาวน์โหลด" vs "บันทึกลงเครื่อง" ไม่เหมือนกันในสายตาลูกค้าคนละกลุ่ม
- ห้ามปล่อยให้แปลจากอังกฤษตรงๆ จะได้ภาษาแข็งแบบคู่มือเครื่องใช้ไฟฟ้า — สั่งว่า *"เขียนใหม่เป็นไทย ไม่ใช่แปล"*
- ให้ตัวอย่างแบรนด์ไทยที่ชอบโทนของเขามา 1 อัน ได้ผลกว่าอธิบายโทนเป็นคำพูด
- ปุ่มและ error message ภาษาไทยยาวกว่าอังกฤษ ~30% — บอกลิมิตตัวอักษรไปด้วย ไม่งั้น UI แตก

## 9. มุมมองซีเนียร์ — ตัดกฎทิ้งเกือบหมด

ตารางทั้งหมดข้างบนคือของมือใหม่ที่ต้องมีกฎกำกับ ซีเนียร์คิดแค่นี้:

```
default: Sonnet 5 ทุกอย่าง
  ↑ ขึ้น Opus   เมื่อ "รู้สึกว่ายาก" หรือ "พลาดแล้วเจ็บ"
  ↓ ลง Haiku   เมื่อ "ไม่ต้องคิดเลย" และมีเยอะพอจะคุ้ม
```

| | มือใหม่ | ซีเนียร์ |
|---|---|---|
| เริ่มงาน | เปิดตารางหาว่าใช้ตัวไหน | เปิด Sonnet ลุยเลย |
| เจองานยาก | ลังเล ลองตัวถูกก่อน | ขึ้น Opus ทันที ไม่เสียดาย |
| งานถึก | ใช้ Opus เพราะเคยชิน | เด้งลง Haiku / มอบ subagent |
| สลับโมเดล | บ่อย ตามฟีเจอร์ | นานๆ ที ตามสัญชาตญาณ |
| ตอบตื้น | เด้งขึ้นโมเดลทันที | เพิ่ม effort ก่อน แล้วค่อยเด้ง |
| context ยาว | ลุยต่อจนมันเริ่มลืม | `/clear` แล้วเริ่มใหม่พร้อมสรุป |

กฎเดียวที่ซีเนียร์ไม่เคยยอมประหยัด: **"พลาดแล้วเจ็บ" = ใช้ตัวที่ดีที่สุด ไม่ต้องคิด**
(เงิน, auth, migration ลบข้อมูล, decision ที่แก้ทีหลังแพง)

ท่าจริงใน Claude Code: ตัวหลักฉลาดคุมงาน → มอบงานถึกให้ subagent ตัวถูกทำขนาน
เหมือนซีเนียร์จริงที่ไม่ลงมือ format code เอง

> **กฎทอง:** อย่าเลือกโมเดลให้เยอะกว่าเลือกโค้ด
> เวลาที่เสียไปนั่งเลือกโมเดลเป๊ะๆ ทุกงาน แพงกว่าส่วนต่างค่าโมเดลที่ประหยัดได้
